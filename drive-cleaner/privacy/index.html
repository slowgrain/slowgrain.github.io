2. Google user data and permissions

The app requests https://www.googleapis.com/auth/drive to list and read files accessible to the signed-in account and, when the user requests cleanup or restoration, move files to or restore files from Drive Trash. The app does not permanently delete or share files. This full Drive scope supports whole-Drive and folder indexing, file-list tools, sharing audits, scheduled cleanup, operation history and restore, and analysis of files selected in Picker. The signed-in user chooses the scan scope. The app does not start an unrequested background scan. Apps Script triggers run only when configured by the user.

Drive data processed may include file IDs, names, MIME types, parent folders, sizes, checksums, creation and modification timestamps, versions, ownership and capabilities, image/video dimensions and video duration, previews and derived analysis fingerprints, sharing-permission metadata, and Drive storage-usage figures. This data is used only for duplicate/similarity review, user-requested cleanup and restore, and user-selected reports.

OAuth scopes

  • drive: reads Drive file lists and metadata and moves or restores files when requested by the user. It also enables whole-Drive scans and Picker-selected file access.
  • drive.appdata: stores, reads, and deletes the app's index, analysis fingerprints, reports, and operation history in the user's hidden appDataFolder.
  • script.scriptapp: creates and manages Apps Script triggers for scans, cleanup, and reports the user enables.
  • script.external_request: requests Google Drive API previews and app-data file I/O from Apps Script, and verifies transactions with Paddle when the user starts a purchase.
  • script.send_mail: sends summary email to the account owner only if the user separately enables email reports.

The app does not separately request drive.file; the broader drive scope is required for whole-Drive features. Users may revoke access in their Google Account security settings. Features that need revoked access will stop working.

3. Where data is processed and stored

  • Apps Script user properties: account license, scheduled settings, some analysis state, and report-delivery state.
  • The user's hidden Drive app data folder: whole-Drive file index, derived fingerprints, storage/sharing snapshots, and cleanup/restore operation history. The app does not place these files in an ordinary visible Drive folder.
  • Browser: some selected media analysis runs in the browser. Reduced analysis fingerprints may be saved in browser IndexedDB to avoid repeating work. Interface preferences are saved in browser local storage.
  • Apps Script server: proxies thumbnail preview requests to Google APIs and returns the result to the browser. It is not used as a file repository.
  • Optional local analysis helper: only after the user connects it, the app passes selected file IDs, version/checksum metadata, and a short-lived Google OAuth token to a helper running on the user's computer at 127.0.0.1. The helper temporarily downloads requested originals for FFmpeg and related analysis, then removes temporary source files when a job ends. Derived fingerprints and resume checkpoints may remain in the user's local cache. The app currently has no function to delete this separate cache; the user can stop the helper and manually remove .cache/drive-cleaner-helper in the home folder (on Windows, %USERPROFILE%\.cache\drive-cleaner-helper). The helper requires separate installation and an explicit connection.

4. Email and payments

If the user enables scheduled reports and email delivery, reports go to the Drive account owner's email address. A report may include file counts, duplicate summaries, storage figures, and cleanup results selected by the user. The app does not read Gmail.

If Paddle billing is enabled, Paddle processes payment and billing data directly. The app verifies transaction and subscription identifiers and stores app-license state in user properties. The items Paddle collects, retention, and refund handling are governed by Paddle's policy and checkout. Paddle products, prices, credentials, and transactions have not yet been configured or verified for the current deployment, so payment data is not collected until checkout is enabled.

5. Sharing, sale, advertising, and analytics

The app does not sell Google user data or use it for advertising. It does not expose file contents or lists to other users. Cleanup and restoration follow the signed-in account's permissions and the user's selected action. The app currently contains no third-party advertising or product-analytics SDK. Paddle acts as a payment processor only when the user starts checkout.

6. Retention and deletion

Indexes, fingerprints, settings, and operation history remain until the user deletes app data; there is currently no automatic expiry. Reports retain up to the latest 400 snapshots. The user can select Privacy and app data → Delete my app data to delete app-owned storage files, app user properties, app triggers, and the app analysis cache and preferences in the current browser. This does not change original Drive files. Revoking Google access does not itself delete stored app data; delete app data before revoking access where possible. If deletion reports an error, contact slowgrain.dev@gmail.com.

The in-app deletion action does not delete a separate local-helper cache, Google security/diagnostic logs, or transaction records Paddle must retain by law. The user must stop the helper and manually remove its cache folder on the computer. Drive access can be revoked separately in Google Account settings. Files in Drive Trash can be restored or permanently deleted by the user in Drive.

7. Security and policy

The app does not expose OAuth tokens in its UI or store them in its own database. When a local helper connection is used, the token is held in memory only for the job and discarded after expiry. Google Apps Script, Google Drive, and Paddle security controls and policies also apply. No internet transmission or third-party platform can be guaranteed risk-free.

The use and transfer of information received from Google APIs adheres to the Google API Services User Data Policy, including the Limited Use requirements. Google user data is not used to train generalized artificial intelligence or machine-learning models. The provider does not read file content for support without the user’s affirmative permission, except where required for security or by law. Material changes to data handling will be reflected here with an updated effective date.
